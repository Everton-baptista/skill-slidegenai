# Create a complete presentation

Use for a request to create slides, with or without a visual reference. Identity extraction is a supporting operation when relevant, not the default final deliverable.

## Start from what the user provided

Identify topic, supplied content, audience, purpose, output language, count and format. Preserve explicit requirements. Infer reversible choices from context; ask only for information that would materially block the work. A topic-only request can become a researched or illustrative outline when appropriate. Do not invent business performance or empirical claims to fill a layout.

Choose the mode:

| Input | Action |
| --- | --- |
| Topic or outline, no visual reference | Author an original visual direction and build the deck |
| Named catalog direction | Use its character as a starting point; adapt layouts to the actual message |
| Website/brand guide | Acquire relevant evidence/assets, then create; separate observations from authored choices |
| Template to reproduce faithfully | Import/clone it where possible; preserve the supplied system |
| Existing deck for content only | Retain its facts; do not assume its design must control the new presentation |

For original work, choose a concrete concept, palette, display/body roles, image strategy and recurring alignment relationships. The [font pack](font-pack.md), [expressive typography](expressive-typography.md) and [art-direction guide](art-direction.md) provide options. Avoid choosing a generic blue sans-serif theme solely because the user supplied no brand reference. Blue and sans-serif remain valid when the subject warrants them.

## Plan and author

Build a useful narrative from the source: context, proposition, explanation/evidence and a meaningful close when appropriate. Honor the requested count; include topic covers inside that total when they help. Map each message to a composition. Vary density, image role and scale while keeping a coherent visual signature. Use a chart for supported quantitative comparisons, a flow for actual relationships, and text/image layouts when those communicate better.

Use the available slide editor, native API or HTML authoring tool to create the actual artifact. The skill controls design and review decisions; a host editor executes them. No Python helper or particular slide engine is mandatory. Keep text and requested analytical objects editable where supported. Resolve available fonts and images early enough to measure real content, but continue independent content work while assets are acquired.

A missing optional reference or asset should lead to an appropriate original/typographic/native-diagram alternative, not a menu asking the user to finish the job. If real product photography is essential, pursue the available acquisition/import paths in [website assets](website-assets.md). Do not replace a required real photograph with an undisclosed generated approximation.

## Working records without invented evidence

Use files when batching, repeatability or packaging needs them. For an original deck, record authored choices in `design-system.json`/the plan, with no implication of official brand compliance. If a reusable package requires a version-1 profile, first save an actual local creative brief describing the supplied request and authored decisions. Reference that real `local-file` source; classify designer-selected rules as `inferred`. Do not label them `observed` or `user-approved` merely because the user requested a presentation. A normal deck does not need to become a brand-specific skill.

## Finish the request

Render and inspect every slide and the overview when tools permit. Check the exported artifact itself, including native evidence and font substitution. Deliver the supported artifact, previews and concise limitations. State exactly what was produced; “I could create this if you upload more material” is not completion when available tools and reasonable assumptions already permit useful work.

If a host lacks file authoring, supply a storyboard/content draft and explain the format limit. If it can author but cannot render, deliver the file as an unverified visual draft. Do not turn a missing renderer into a claim that no file can be created.
